JavaScript Engine

What is a JS Engine?

A JavaScript engine is a program (or interpreter) that reads, compiles, and executes JavaScript code. It converts human-readable JS source code into machine code that the CPU can execute directly.

Popular JS Engines

  • V8 — Google Chrome, Node.js (C++)
  • SpiderMonkey — Mozilla Firefox
  • JavaScriptCore (Nitro) — Safari / WebKit
  • Chakra — Old Microsoft Edge
  • Hermes — React Native (Meta)

Engine Responsibilities

  • Parse source code into AST
  • Compile bytecode / machine code
  • Optimize hot code paths (JIT)
  • Manage Call Stack & Heap
  • Run Garbage Collection
  • Expose built-in APIs
JS Engine High-Level View
Source Code (.js) → Parser → AST → Interpreter → JIT Compiler → Machine Code
02

How Does the JS Engine Work?

Step 1 — Parsing

The engine reads the raw source code character-by-character. The Lexer (tokenizer) splits it into tokens, then the Parser builds an Abstract Syntax Tree (AST) that represents the code structure.

Step 2 — Compilation

Modern engines use JIT (Just-In-Time) compilation. The AST is first converted to bytecode by an interpreter (e.g., V8's Ignition), then hot code paths are recompiled to optimized machine code by a compiler (e.g., V8's TurboFan).

Step 3 — Execution

The engine uses a Call Stack to track function calls (LIFO). The Heap stores objects and dynamic data. The Event Loop coordinates async operations via the Callback Queue and Microtask Queue.

Step 4 — Optimization

The engine profiles running code. Functions called many times ("hot") get recompiled to faster machine code. If an assumption breaks (deoptimization), it falls back to bytecode. This cycle repeats continuously.

V8 Internals (Detailed)
Source JS → Lexer → Tokens → Parser → AST
Ignition (Interpreter) → Bytecode → TurboFan (JIT) → Machine Code → CPU Executes
Profiler monitors hot functions ⟳ Deoptimize if needed

Memory Areas

  • Call Stack — tracks execution context, primitive values, function frames
  • Heap — dynamic memory for objects, arrays, closures
  • Stack Frame — each function invocation pushes a new frame
  • Stack Overflow — too many recursive calls exceed stack size limit
03

Garbage Collector

What is a Garbage Collector?

A Garbage Collector (GC) is an automatic memory management process within the JS engine. It identifies memory that is no longer reachable (referenced) by the program and reclaims it, freeing up the heap for new allocations.

Mark-and-Sweep Algorithm

The primary GC algorithm used in V8:

  • Mark Phase: Starting from "roots" (global, stack), traverse and mark all reachable objects
  • Sweep Phase: Any unmarked object is considered dead and its memory is freed
  • Compact Phase: Optionally compacts memory to reduce fragmentation

V8 GC Generations

  • Young Generation (Scavenger): New objects live here. Short-lived. Collected frequently and fast.
  • Old Generation (Major GC): Objects that survive multiple young GC cycles are promoted here. Collected less often.
  • Large Object Space: Objects too large for other spaces.

Reachability — The Core Concept

An object is "alive" if it is reachable from a root. Roots include global variables, currently running functions, and the call stack. Unreachable objects — those with no path from any root — are garbage-collected.

GC Reachability Graph
Root (Global) → Object A (alive) → Object B (alive)
Object C (no reference → unreachable) → COLLECTED 🗑

Memory Leak

What is a Memory Leak?

A memory leak occurs when your program allocates memory but never releases it — even when it's no longer needed. Over time, this exhausts available memory, causing slowdowns, crashes, or tab kills in browsers.

Common Causes

  • Global Variables: Accidentally creating globals that persist forever
  • Forgotten Timers: setInterval referencing objects that should be freed
  • Detached DOM Nodes: Removed from DOM but still referenced in JS
  • Closures: Closures keeping large outer scope alive unintentionally
  • Event Listeners: Listeners not removed when elements are destroyed
  • Caches: Unbounded caches growing forever

How to Detect & Fix

  • Use Chrome DevTools → Memory tab → Heap Snapshot
  • Monitor Allocation Timeline for growth patterns
  • Use WeakMap / WeakSet for object caches (GC-friendly)
  • Always call removeEventListener on cleanup
  • Clear setInterval and setTimeout refs
  • Nullify references to large objects when done

WeakRef & WeakMap — The Solution

Use WeakMap and WeakSet when you want to associate data with objects but allow GC to reclaim them when no other references exist. WeakRef holds a weak reference to an object, allowing it to be collected. These are powerful tools for caches and registries.

Playwright

What is Playwright?

Playwright is an open-source end-to-end testing and browser automation framework developed by Microsoft. It allows you to write scripts that control real browsers (Chromium, Firefox, WebKit) programmatically, enabling robust automated testing of web applications.

Key Features

  • Cross-browser: Chromium, Firefox, WebKit (Safari) from one API
  • Cross-platform: Windows, macOS, Linux
  • Auto-wait: Automatically waits for elements to be ready
  • Network interception: Mock/modify HTTP requests
  • Screenshots & Videos: Built-in capture on failure
  • Trace Viewer: Step-by-step execution playback
  • Parallel execution: Run tests in parallel workers
  • Multiple languages: JS/TS, Python, Java, C#
  • Headless & headed: Flexible execution modes
  • Mobile emulation: Device viewports and touch

Playwright vs Puppeteer vs Selenium

  • Playwright: Multi-browser, auto-wait, modern API, Microsoft
  • Puppeteer: Chromium/Firefox only, lower-level, Google
  • Selenium: Oldest, WebDriver-based, slower, all browsers
  • Playwright has superior reliability due to smart waiting strategies
  • Built-in test runner (@playwright/test)

Playwright Architecture

Playwright uses a client-server architecture. The Node.js (or Python/Java/C#) client communicates with a Playwright Server over a WebSocket connection. The server manages browser instances via the browser's native protocol (CDP for Chromium, Firefox Remote Debugger Protocol, WebKit Inspector Protocol).

Playwright Architecture
Test Script (Node/Python/Java) → WebSocket → Playwright Server
Playwright Server ↓
CDP (Chromium) | RDP (Firefox) | WIP (WebKit)
Browser Process → Browser Context (isolated) → Page / Frame

Browser Context

A BrowserContext is an isolated environment within a browser instance — similar to an incognito window. It has its own cookies, storage, and permissions. Each test can get its own context for isolation without launching a new browser process, making tests fast and independent.

06

Node.js

What is Node.js?

Node.js is an open-source, cross-platform JavaScript runtime environment built on Google's V8 engine. It allows JavaScript to run outside the browser — on servers, command-line tools, and desktop apps. Created by Ryan Dahl in 2009.

Core Architecture

  • V8 Engine: Compiles and executes JS
  • libuv: C library providing the Event Loop, async I/O, thread pool
  • Node.js Bindings: Bridge between JS and C++ libraries
  • Node.js Standard Library: fs, http, path, etc.
  • npm: World's largest package registry

Event Loop in Node.js

  • Timers: setTimeout, setInterval callbacks
  • Pending I/O: I/O callbacks from last iteration
  • Idle/Prepare: Internal use only
  • Poll: Retrieve new I/O events
  • Check: setImmediate callbacks
  • Close: Close event callbacks

Single-Threaded but Non-Blocking

Node.js is single-threaded for JavaScript execution, but uses libuv's thread pool for expensive operations (file system, DNS, crypto). This means I/O operations don't block the main thread — callbacks fire when the operation completes, keeping the Event Loop free to handle more requests.

Node.js Runtime Architecture
JS Code → V8 Engine ↔ Node.js APIs (C++ Bindings)
Node.js APIs → libuv (Event Loop + Thread Pool) → OS (Network / FS / Timers)

Browser Engine & Rendering Engine

Browser Engine vs Rendering Engine

A Browser Engine (also called layout engine or rendering engine) is the core software component that parses HTML/CSS and renders web pages visually. The JavaScript engine is a separate component that the browser embeds alongside the rendering engine.

Major Rendering Engines

  • Blink — Chrome, Edge, Opera, Brave (forked from WebKit 2013)
  • WebKit — Safari, iOS browsers
  • Gecko — Firefox
  • Trident / EdgeHTML — Old IE / Old Edge (deprecated)

Critical Rendering Path

  • Parse HTML → DOM Tree
  • Parse CSS → CSSOM Tree
  • Combine → Render Tree
  • Layout → Calculate positions and sizes
  • Paint → Draw pixels to layers
  • Composite → Combine layers for display
Critical Rendering Path
HTML → DOM Tree + CSSOM Tree → Render Tree
Render Tree → Layout (Reflow) → Paint (Repaint) → Compositing → Screen

Reflow vs Repaint

  • Reflow: Recalculate layout geometry (triggered by size, position changes). Expensive.
  • Repaint: Redraw pixels without layout change (color, visibility). Cheaper than reflow.
  • Compositing: GPU combines pre-painted layers. Cheapest — target with transform & opacity.

Browser Main Components

  • UI Layer — Address bar, back/forward buttons
  • Browser Engine — Orchestrates UI and rendering
  • Rendering Engine — Displays content (Blink/WebKit/Gecko)
  • Networking — HTTP/HTTPS requests
  • JS Engine — V8, SpiderMonkey, etc.
  • Data Storage — Cookies, IndexedDB, localStorage

Interview Questions

🔧 JS Engine
What is a JavaScript engine and how does it differ from a runtime? +
Easy A JS Engine (e.g., V8) is the component that parses, compiles, and executes JavaScript code. It manages the Call Stack and Heap. A JS Runtime (e.g., Node.js, Browser) is a larger environment that embeds the engine and adds extra APIs — like the DOM, setTimeout, fetch, or Node's fs module. The engine alone cannot do I/O; the runtime provides those capabilities.
What is JIT compilation? How does V8 use it? +
Medium JIT (Just-In-Time) compilation compiles code at runtime rather than ahead of time. V8 uses a two-tier approach: Ignition (interpreter) quickly generates bytecode for fast startup, then a profiler identifies "hot" functions called repeatedly. TurboFan (optimizing compiler) recompiles those hot functions into highly optimized machine code. If an optimization assumption is violated, it deoptimizes back to bytecode (bailout). This balances startup speed with peak performance.
What is an AST (Abstract Syntax Tree) and why does the engine need it? +
Medium An AST is a tree data structure that represents the syntactic structure of source code. Each node represents a construct (variable declaration, function call, binary expression, etc.). The parser converts source code → tokens → AST. The engine needs it because raw text is ambiguous and hard to analyze; the AST is a structured, traversable representation that compilers and interpreters can work with efficiently. Tools like Babel, ESLint, and Prettier also consume ASTs to transform or analyze code.
What is hidden class optimization in V8? +
Hard V8 assigns hidden classes (shapes) to objects to optimize property access. When you create objects with the same properties in the same order, V8 gives them the same hidden class and can use fast property lookup. If you add properties in different orders or add them later, V8 creates new hidden classes, slowing things down. Best practice: always initialize all object properties in the constructor in the same order. Avoid adding properties outside the constructor.
⚙️ How JS Engine Works
Explain the Call Stack and how it works in JavaScript. +
Easy The Call Stack is a LIFO (Last In, First Out) data structure that tracks execution contexts. When a function is called, a stack frame is pushed containing local variables, parameters, and a return address. When the function returns, its frame is popped. JavaScript is single-threaded, so only one function executes at a time. A Stack Overflow occurs when too many frames accumulate (e.g., infinite recursion) and the stack exceeds its memory limit.
What is the Event Loop and how does it work? +
Medium The Event Loop continuously checks: if the Call Stack is empty, take the first task from the Microtask Queue (Promises, queueMicrotask) and push it to the stack. After all microtasks are done, take the next task from the Macrotask Queue (setTimeout, setInterval, I/O). Microtasks always have priority over macrotasks. This mechanism enables asynchronous behavior despite JS being single-threaded.
What is the difference between the Stack and the Heap? +
Easy The Stack stores static memory — primitive values (number, boolean, string, null, undefined), references to heap objects, and execution frames. It's fast and managed automatically (LIFO). The Heap stores dynamic memory — objects, arrays, functions, and closures. It's larger and unordered; the GC manages it. When you do const obj = {}, the reference lives in the stack but the actual object data lives in the heap.
🗑️ Garbage Collector
How does the Mark-and-Sweep algorithm work? +
Medium Phase 1 — Mark: The GC starts from "roots" (global objects, call stack variables). It traverses all object references recursively and marks every reachable object. Phase 2 — Sweep: The GC iterates through the entire heap. Any object that was NOT marked is considered unreachable (garbage) and its memory is freed. Phase 3 — Compact (optional): Remaining live objects are moved together to eliminate fragmentation, making future allocations faster.
What is the difference between young and old generation GC in V8? +
Hard V8 uses generational GC based on the hypothesis that most objects die young. Young Generation (Scavenger/Minor GC): New objects are allocated here. Collection is very fast (milliseconds) using a semi-space copying algorithm. Objects surviving 2+ cycles are "promoted." Old Generation (Major GC): Long-lived objects live here. Uses Mark-Sweep-Compact. Runs less frequently but takes longer. Incremental & Concurrent GC spreads work across multiple JS execution pauses to avoid long freezes.
Can you force garbage collection in JavaScript? +
Easy No — you cannot directly force GC from JavaScript. The engine decides when to run it. However, you can hint at it by: (1) setting variables to null to remove references, (2) using WeakRef/WeakMap so objects can be collected when no strong references exist. In Node.js, --expose-gc flag enables global.gc() for testing purposes only — never use this in production.
💧 Memory Leak
How would you detect a memory leak in a web application? +
Medium Use Chrome DevTools → Memory tab: (1) Heap Snapshot — take snapshots before/after a user action and compare. Look for objects accumulating. (2) Allocation Timeline — record allocations over time; a steadily growing heap indicates a leak. (3) Allocation Sampling — see which functions allocate the most. In Node.js, use --inspect with Chrome DevTools or tools like clinic.js, heapdump, or memwatch-next.
How can event listeners cause memory leaks and how do you prevent it? +
Medium When you add an event listener to a DOM element, the browser keeps a reference to both the element and the listener's callback (and its closure). If the element is removed from the DOM but you haven't called removeEventListener, the element and all objects in the closure remain in memory. Prevention: always call element.removeEventListener(type, handler) in cleanup logic (e.g., React's useEffect cleanup, component's disconnectedCallback). Alternatively, use AbortController to remove multiple listeners at once.
What is a detached DOM node and how does it cause a leak? +
Hard A detached DOM node is a node that has been removed from the DOM tree but is still referenced by a JavaScript variable. For example: let el = document.getElementById('btn'); el.remove(); — the node is gone from the page, but the el variable still holds a reference. The GC sees this as reachable and won't collect it. If el references a large subtree, all those nodes and their event handlers stay in memory. Fix: set el = null after removal and ensure no other references exist.
🎭 Playwright
What is a BrowserContext in Playwright and why is it important? +
Medium A BrowserContext is an isolated session within a browser process — equivalent to a fresh incognito window. It has its own cookies, localStorage, sessionStorage, cache, and permissions. It does NOT share state with other contexts. This is critical for test isolation: each test gets its own context, preventing state leakage. Multiple contexts can run in the same browser process simultaneously, making it far more efficient than launching separate browser instances per test.
How does Playwright's auto-wait differ from Selenium's explicit waits? +
Medium In Selenium, you must explicitly write waits (implicit, explicit, fluent) before every interaction, or your test becomes flaky. In Playwright, every action (click, fill, check) automatically waits for the element to be: (1) attached to DOM, (2) visible, (3) stable (no animations), (4) enabled, (5) receives events. This built-in auto-wait eliminates most flakiness without boilerplate. You can still use waitForSelector or waitForResponse for specific cases.
What is Playwright's Page Object Model (POM) pattern? +
Medium The Page Object Model is a design pattern where each page (or component) of your app is represented as a class. The class encapsulates all locators and actions for that page. Tests interact with page objects rather than raw selectors directly. This improves: Maintainability — selector changes only need to be updated in one place; Readability — tests read like user stories; Reusability — same page object used in multiple tests. Playwright's fixtures make injecting page objects into tests elegant.
How does Playwright handle network interception? +
Hard Playwright allows intercepting network requests via page.route(urlPattern, handler). You can: mock responses (return fake data without hitting the server), modify requests (change headers, body), block requests (ads, analytics), or abort requests. This is invaluable for testing loading states, error states, and offline behavior. page.waitForRequest() and page.waitForResponse() let you assert on specific network activity. HAR files can also be recorded and replayed.
🟢 Node.js
How is Node.js non-blocking if JavaScript is single-threaded? +
Medium JavaScript itself runs on a single thread, but Node.js uses libuv — a C library that provides a thread pool (default 4 threads) for expensive operations like file system access, DNS lookup, and crypto. When you call fs.readFile(), Node.js delegates it to libuv's thread pool. The main JS thread is free to handle other requests. When the I/O completes, the callback is pushed to the Event Loop queue and executed on the main thread. Network I/O uses OS-level async mechanisms (epoll/kqueue), not threads.
What is the difference between process.nextTick() and setImmediate()? +
Hard process.nextTick() fires at the end of the current operation, before the Event Loop moves to the next phase — it's not part of the Event Loop. It runs after synchronous code but before any I/O or timers. setImmediate() fires in the Check phase of the Event Loop — after I/O callbacks. Order: synchronous code → nextTick → microtasks (Promises) → I/O callbacks → setImmediate → timers (setTimeout). Excessive nextTick usage can starve the Event Loop.
What are Streams in Node.js and why are they useful? +
Medium Streams are a way to handle data piece-by-piece (chunks) rather than loading everything into memory at once. Types: Readable (source), Writable (destination), Duplex (both), Transform (modify while passing through). Why useful: processing a 10GB file by loading it all into memory would crash the server. Streaming reads/writes in chunks, keeping memory usage constant. Use .pipe() to chain streams. Real-world: video streaming, file uploads, HTTP request body processing.
🌐 Browser & Rendering Engine
What is the Critical Rendering Path and how can you optimize it? +
Medium The Critical Rendering Path is the sequence: HTML → DOM → CSSOM → Render Tree → Layout → Paint → Composite. Optimizations: (1) Minimize render-blocking CSS — inline critical CSS, load non-critical CSS async. (2) Defer non-critical JS with defer/async attributes. (3) Minimize DOM size. (4) Avoid forced synchronous layouts (reading layout properties immediately after writing). (5) Use CSS transform and opacity for animations — they only trigger compositing, not layout/paint.
What is the difference between Reflow and Repaint? Which is more expensive? +
Easy Reflow (Layout): Recalculating geometry — positions, dimensions. Triggered by changes to element size, position, font, adding/removing DOM elements, or reading layout properties like offsetWidth, getBoundingClientRect(). Reflow affects the element AND all its descendants (and potentially ancestors). Repaint: Redrawing pixels without geometry change — triggered by color, background, border-color, visibility changes. Cost order (cheapest → most expensive): Compositing → Repaint → Reflow. Batch DOM writes, use documentFragment, or requestAnimationFrame to minimize reflows.
What is "layout thrashing" and how do you avoid it? +
Hard Layout thrashing (forced synchronous layout) happens when you interleave DOM reads and writes in a loop, forcing the browser to recalculate layout on every read. Example: reading el.offsetWidth inside a loop that also changes el.style.width on every iteration — the browser can't batch its work. Fix: (1) Read all values first, then write all values — batch reads and writes separately. (2) Use requestAnimationFrame to schedule visual changes. (3) Use the ResizeObserver API instead of polling. Libraries like FastDOM help enforce read/write batching.
How does the browser parse HTML with external scripts and stylesheets? +
Medium The HTML parser runs top-to-bottom. CSS: Stylesheets block rendering (not parsing) — the browser needs CSSOM to build the Render Tree. Scripts without attributes: Block HTML parsing entirely — parser stops, script fetches and executes, then parsing resumes. async scripts: Fetch in parallel, execute immediately when ready (may execute out of order). defer scripts: Fetch in parallel, execute after parsing complete, in order — best for most scripts. Speculative parsing (preload scanner): Browsers look ahead in the HTML to preload resources even while blocked.
